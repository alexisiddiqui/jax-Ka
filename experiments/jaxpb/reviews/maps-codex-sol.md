## Why CPU maps stayed flat

Grouping four sites at a time reduces peak live scratch. The baseline maps-only test already showed **4.36 → 3.55 s/site** at B=4 on one state. Phase 1 kept much of that memory benefit, but it still executes repeated gather, norm, reduction and scatter passes over large query and probe lists. CPU tiles are only **539 atom rows or 404 probe rows** at reach 1. In full groups, `all(cnt > 0)` and `all(npreg > 0)` test whether each lane has *any* work. A lane that finishes early can still execute tiles until the longest lane finishes. If one lane starts at zero, the whole stage uses the per-site loop, with a condition on every tile. [B-only sizing test](results/profile2.json:629), [maps.py:356](src/jaxpb/maps.py:356), [maps.py:580](src/jaxpb/maps.py:580)

The likely CPU time sinks are **candidate evaluation and intermediate memory traffic**, **probe reach scatter**, and **repeated probe indexing**. Each active site still sorts the padded whole-molecule probe input for coarse and focused maps, searches the cell ranges twice, and scans the probes again for region compaction. CSR removes the dense table write. It leaves those scans and sorts in place, and one occupied slab still evaluates masked slots across all 27 offsets. The archived CPU run shows the three small `4066` states improving while the two larger states lose enough time to erase those gains. The final **14.08 GB** is the whole-process peak, set during SOR. [maps.py:59](src/jaxpb/maps.py:59), [maps.py:193](src/jaxpb/maps.py:193), [maps.py:397](src/jaxpb/maps.py:397), [archived CPU runs](results/opt1-evidence.tar.gz), [OPT1-REPORT.md:25](OPT1-REPORT.md:25)

## Correctness and parity

- **Site validity is inferred from model radii.** A real site with no positive model radius passes record validation but is treated as padding, suppressing its whole-molecule maps and overflow counters. Pass a fixed-shape validity mask from the site layout. Also normalize the inactive outputs in mixed CPU groups if callers inspect them. Those lanes currently flow through output assembly, while fully inactive groups return `empty_maps`. [records.py:282](src/jaxpb/records.py:282), [maps.py:453](src/jaxpb/maps.py:453), [maps.py:606](src/jaxpb/maps.py:606)
- **Configurable CPU batch sizes can now fail.** `PBConfig.B` is configurable, but `B=5`, for example, now raises in `maps_batch`. Use a static divisor or internally pad to a multiple of four and slice back to `B`. [pb.py:326](src/jaxpb/pb.py:326), [maps.py:597](src/jaxpb/maps.py:597)
- **The finite-distance tie merge is sound.** Its key is `offset * K + slot`, with stable original point order within each cell. Overflow uses uncapped occupancy before candidate truncation. Preserve both, along with the exact `norm(q - p) - w` expression and the empty-row sentinel. The CPU `B=1` tail already changed `esolvS` bits, so check `surf` directly when changing projection shapes or fusion. Compare against the frozen dense revision because `maps_batch_ref` now shares the changed query helper. ## Ranked fix plan

The gain ranges are planning estimates and overlap.

1. **A40: restore dense atom gathers and widen atom and reach tiles independently.** Start at **1,536–2,048** rows for normal atom queries, **384–512** for reach-2 culling, and **2×** the current reach-scatter tile. Estimated gain **0.6–1.3 s/state**. Dense atom tables cost about **22 MB normal or 45 MB XL** per B=16 batch. The wider tiles add several hundred MiB to the nominal scratch budget, so gate on compiled peak allocation. Parity risk is low for the gather and moderate for changed fusion. [maps.py:49](src/jaxpb/maps.py:49), [maps.py:108](src/jaxpb/maps.py:108), [maps.py:556](src/jaxpb/maps.py:556)
2. **A40: give probe projection a fixed 64- or 128-slot one-shot path, with the ranked CSR fallback.** Select from actual queried occupancy and verify how often each width would be used. Reduce `(distance, original rank, point id)` together to remove the two post-reduction gathers in the fallback. Estimated gain **0.4–1.0 s/state**. At the same width in query rows, candidate scratch grows **2–4×** for those tiles. Budget probe rows separately. A full dense coarse probe table alone costs **11.16 GB** at normal K. Dense fine or model tables are about **287 MB each** and worth considering only with a separate candidate scratch limit. Parity risk is moderate at width boundaries and cross-slab ties. [maps.py:126](src/jaxpb/maps.py:126), [maps.py:525](src/jaxpb/maps.py:525)
3. **Hoist activity checks and preserve vector width on useful work.** Give full GPU batches a direct vectorized path and use a small fixed set of internal widths for GPU tails. On CPU, keep B=4 projection arithmetic and split query and reach processing into a common batched prefix and a guarded suffix. Estimated gain **0.1–0.4 s/state on A40**, with CPU benefit concentrated in uneven groups. Scratch stays in the current range. CPU parity risk is moderate if a suffix changes floating-point lowering. [maps.py:348](src/jaxpb/maps.py:348), [maps.py:580](src/jaxpb/maps.py:580), [maps.py:614](src/jaxpb/maps.py:614)
4. **CPU: reduce work per row and per probe.** Keep CSR, derive starts and stops from a cell histogram and prefix sum while retaining stable `order`, and compact actual candidates before computing distances. Keep the original rank and a fixed-capacity fallback. For reach, skip site/axis passes with no `need` points and tune CPU tiles separately for gathers and scatter. Estimate **10–25% lower CPU maps time** if those passes dominate a CPU trace. Scratch scales with a tile plus the cell histogram. Parity risk is moderate for candidate compaction and low for skipping a reach mask that cannot be consumed. **Defer query sorting** until irregular gathers are measured after these changes. Regular grid rows already have spatial locality. Sorting compacted contact and projection rows has a plausible **0–5%** stage gain, costs a permutation and inverse permutation, and must restore row order before scatter. [maps.py:59](src/jaxpb/maps.py:59), [maps.py:465](src/jaxpb/maps.py:465), [maps.py:487](src/jaxpb/maps.py:487)

Use the existing class and normal/XL signatures for all four changes. Keep occupancy and tail decisions inside those executables. The acceptance bar is **≤3.40 s/state Pallas, ≤3.12 XLA, and a repeatable CPU improvement**, with compiled map scratch and process peak reported separately. Gate on bytewise active `ex/ey/ez`, `ion`, `bidx`, `surf`, and counters, then the existing pipeline parity and zero-warm-compile checks. [BUILD-OPT1.md:25](BUILD-OPT1.md:25)
